## 1. The common thread

All 45 ideas assume the assurance chain itself works:
- every citation is true;
- every sign-off is real;
- a number stays where it was put;
- the reader's only question is "is this number true?".

The r7 audit shows the first assumption failed in this repository (C001, C059: synthetic figures emitted under
Barrick's name). The other three have never been tested. The four ideas below each remove one of those
assumptions.

## B1. Source-sensitivity witnesses: provenance that can fail

### The blind spot

- **What the system promises.** Every number is a Claim with provenance (INV-001), and GATE-BULL-01 requires
  "zero uncited numbers".
- **Why that promise was hollow.** A citation is a statement the producer writes, and nothing tests it.
  - FACT: the loader substitutes generated bytes when a read fails, keeping the real file's path as the label
    (`crates/fmine-io/src/xlsx.rs:124–128`, `crates/fmine-public/src/lib.rs:236–241`; r7 C001, C059).
  - FACT: `fmine claim show` returns `Exact`/`KnownKnown` for any `clm_` id (r7 C062, PARTIALLY_SUPPORTED).
  - FACT: the AISC bridge's `l_jv` is computed as `cons_sales − (cons_sales − 17.0)`, so it equals 17 for every
    input, though it reads as derived from a workbook cell (`crates/fmine-public/src/lib.rs:343–345`).
  - FACT: the North Mara example is built from literals (`crates/fmine-public/src/lib.rs:437–446`).
- **What has been done about it.** r7 R001 removes the two fallbacks it found. R004 makes the state root change
  when any input byte changes. Neither tests whether *each value* depends on what it cites. A root can commit to
  the real file while the value came from somewhere else.

### Subsystems, user and workflow

- **Subsystems:**
  - Plumb (`fmine-claim`: the witness becomes part of a Claim's provenance);
  - Portal (`fmine-io`, `fmine-public`: perturbed input copies);
  - Testpit (`fmine-verify`: offline re-check).
- **Users:**
  - the named GATE-BULL-01 reviewers (§37.3);
  - the audit committee and external auditor, whose §3 question is "is every disclosed number reproducible?";
  - anyone given an offline bundle;
  - the CFO who will put a figure in front of the board.
- **Workflow.**
  - Every `fmine assure` run also runs itself on perturbed copies of its own inputs, in the same process and
    environment, so a fallback that depends on the environment is exercised the same way.
  - The run emits a witness: seeds, perturbation digests and per-Claim verdicts, committed into R004's state root.
  - `fmine verify witness <bundle>` repeats the check offline.

### Mechanism (DESIGN)

- **Two verdicts per Claim:**
  - **Live:** it changed when its cited cells changed. A Claim that does not change is *decorative*.
  - **Sealed:** it did not change when only uncited cells changed. A Claim that does change has a *hidden
    dependency*.
- **Group testing keeps the cost to a few dozen runs.**
  - Each round perturbs a random half of all numeric cells.
  - For a single-cell extraction Claim, a round checks liveness if its cell is in the perturbed half, and checks
    sealing against any hidden input in that half otherwise.
  - After 20 rounds, a decorative Claim escapes with probability 2⁻²⁰. A single hidden input escapes with
    probability (3/4)²⁰ ≈ 0.3% (INFERENCE).
  - Derived Claims are checked per derivation family (site sums, ownership scaling, YTD sums, AISC ratios).
- **Exactness for linear derivations.** The observed change must equal the declared coefficients times the
  perturbation, in `ExactQty`.
- **Perturbations preserve identities** where the pipeline checks identities, so runs proceed instead of refusing.
- **Two further mutation classes:**
  - deleting a cell must produce a refusal, not a zero (`number_or_zero`, `crates/fmine-public/src/lib.rs:326–341`);
  - removing a file must exit non-zero naming it, which is R001's own acceptance test, reused here.
- **Labels are earned, not written.** An `Exact` evidence class is admissible only when the witness says Live and
  Sealed. That turns C062's asserted label into a computed one.
- **What it cannot catch:** consistent mislabelling (a site or column swap, or a unit scale applied to a whole
  table). Those values are live and sealed but wrong, so they stay with R004(1)'s independent reference read and
  R006's filed-page check. I claim no overlap with those checks.

### First shippable slice

- **Scope.** The extraction layer of the Mine Stats ingest (single-cell Claims), plus the AISC bridge's derived
  Claims.
- **Mechanism.** Perturbed copies are written by rewriting `<v>` values in the sheet XML of a CAS copy of each
  registered workbook.
- **Size.** About 400 LOC plus 20 extra pipeline runs per gate run (INFERENCE; M0's inputs are a few thousand cells
  per workbook).

### Test

- **Known answers from this repository.** At HEAD `68e7091`, without being told where to look, the witness must
  flag:
  - `l_jv` as decorative;
  - the North Mara literals as decorative;
  - the cell-deletion mutation as a missing-to-zero failure;
  - the file-removal mutation as a stand-in substitution.

  r7's findings are the oracle.
- **Synthetic truth.** Seeded pipelines with an injected fallback, a hard-coded literal, a hidden cross-cell
  dependency and a stale cached value. Recall must be 100% and the false-flag rate 0 on clean pipelines.

### What could kill it

- **No unique catches.** After R001/R003 land, two releases and the first M1 site-workbook ingest produce no catch
  that the independent reference read did not also make. Then shrink it to a single regression test and drop the
  verb.
- **Formats that cannot be perturbed faithfully** (PDF tables). Then restrict it to xlsx and CSV.

### Self-score: **760**

It is the only proposal from any of the three of us that would have caught the r7 failure class by
construction. It costs little, and it keeps working as new data paths (site workbooks, MCP answers) arrive.

## B2. Disclosure status: is this number already public, and since when?

### The blind spot

- **Truth is checked; publicness is not.** CC-02, CC-04, COD-02 and AGY-5 all ask whether a number is *true*.
  None asks whether it is *public*. For an executive, and for an AI agent drafting on an executive's behalf, the
  second question carries the legal exposure.
- **The law the plan already names** (FACT, plan §37.3): Barrick files on Form 40-F as a foreign private issuer,
  so Regulation FD does not apply, but the provincial tipping prohibitions explained in National Policy 51-201
  and the US antifraud rules do.
- **Where the plan uses it.** Only to restrict FrankenMining's *own* M0 outputs, never as a product for the
  issuer's disclosure process.
- **Why FrankenMining has the data.** The public lane is a bitemporal record of what was published, when and on
  which basis. Each record carries `availability_time` (INV-016), and the source registry holds retrieval time
  and sha256 (r7 R003). That is exactly the record a disclosure check needs, and no IR tool builds it from
  primary sources.

### Subsystems, user and workflow

- **Subsystems:**
  - Portal (`fmine-public` registry and index);
  - Plumb time (`fmine-time` `as_of`; derivations reuse FMINE-REF-108's look-ahead refusal);
  - Bullion basis rules;
  - Adit (`fmine-mcp` tool `disclosure_status`; illustrative verb `fmine disclosed <draft> --as-of <t>`).
- **Where it runs.** Drafts may contain MNPI, so the check runs in the issuer's tenancy. The public index flows
  one way into the tenancy, consistent with INV-007's monotone taint.
- **Users:**
  - IR and the general counsel's disclosure committee;
  - the CFO and CEO before investor meetings, conferences and analyst calls;
  - the corporate secretary;
  - **executives' AI agents** drafting outbound email, slides or remarks.
- **Verdicts, per quantitative statement in a draft:**

  | Verdict | Meaning |
  |---|---|
  | `Disclosed` | Source, locator, publication time and basis |
  | `DisclosedOtherBasis` | Public only on another basis: 100% vs attributable, or gold vs GEO. The plan records both reserve-replacement bases in one Circular (§1.1 table) |
  | `Derivable` | Arithmetic over disclosed Claims only, each available at or before `as_of`; the derivation is shown |
  | `NotInPublicRecord` | Route to counsel |
  | `ForwardLooking` | Compared with the latest guidance vintage: consistent or outside |
  | `ContradictsDisclosed` | Differs from the disclosed figure on the same basis |

  The tool never says "may be said". INV-002's `regulatory_compliance_claim` stays false, and `Derivable` carries
  a warning: an issuer stating a non-obvious derived figure, such as COD-01's North Mara requirement, can itself
  be new material information.
- **Agent workflow.** The agent calls `disclosure_status` before sending anything external, and stops on
  `NotInPublicRecord`.

### First shippable slice

- **Public lane only.** Index one release package with publication timestamps: the Q2 2026 release figures and its
  two workbooks, plus the prior vintages.
- **A number extractor** that reads unit and basis words.
- **The six verdicts.**

### Test

- **Time-travel oracle.** For every figure first published in the Q2 2026 release:
  - `as_of` = release − 1 day must give `NotInPublicRecord`, or `Derivable` only from earlier disclosures;
  - `as_of` = release + 1 day must give `Disclosed`.

  The bitemporal store supplies the answer key.
- **Synthetic drafts** with seeded labels: sums of disclosed site figures, basis switches, forward-looking ranges,
  near-miss roundings.
- **Asymmetric targets.** A false `Disclosed` is the dangerous error; a false `NotInPublicRecord` is the safe one.
  TARGET: `Disclosed` precision ≥ 99% on the seeded set.
- **Agent test.** A GATE-ROBOT-01 task: "reply to this analyst email using only disclosed figures". The agent must
  call the tool and must not send an undisclosed figure.

### What could kill it

- Counsel will not use the verdicts in pre-clearance.
- IR already keeps a disclosed-facts register with equal coverage.
- The sensitive statements are mostly qualitative ("comfortable with consensus"), so a quantitative check covers
  the wrong part.
- `Disclosed` precision stays below target because the same number appears on different bases.

### Self-score: **640**

New reader, new question, and data the system already holds. It does not go higher because adoption depends on
counsel, and the legal judgment stays human.

## B3. Outbound register: who holds which number, and how they learn it changed

### The blind spot

- **Staleness reaches only readers who read again.** INV-013 marks a Claim stale on read. Board packs, investor
  materials, emailed figures and an agent's memory notes are never read again.
- **The adjacent idea covers decisions, not copies.** COD-04 recalls *decisions* when evidence changes. Nobody
  tracks copies that have left the system.
- **Nobody treats a code defect as a recall trigger.** In the r7 case every output produced through the fallback
  is wrong whatever the evidence says.
- **R001's "before any push" says the same thing.** It is urgent precisely because, after a push, no one could
  list who holds the wrong figures.

### Subsystems, user and workflow

- **Subsystems:**
  - Bedrock (append-only outbound records, INV-003);
  - Plumb (Claim identity, which needs `compute_claim_id` completed first, `crates/fmine-claim/src/lib.rs:312`);
  - Adit (`fmine-report`, export, `fmine-mcp`).
- **Users:**
  - the CFO's office and IR, who correct board packs and investor material;
  - the board secretary;
  - the private-lane data steward and counsel, because GATE-DATA-01 needs an insider list, and this records who
    received which non-public figure, when;
  - executives' AI agents.
- **Workflow.** Every outbound path writes one record:
  - Claim ids and a content digest;
  - code revision and binary digest;
  - the input-manifest root (R004);
  - the recipient principal or agent session;
  - the lane and taint.
- **Queries (illustrative verbs):**
  - `fmine recall --claim <id>`;
  - `fmine recall --revision <rev>`, which lists every output a defective revision produced;
  - `fmine recipients --lane private --since <t>`, which feeds the insider list.
- **Claim leases for agents.**
  - Every MCP answer carries its Claim digest and a revalidation handle.
  - An agent that reuses a remembered figure calls `claim_status(id, digest)` first.
  - A supersession is pushed to subscribed sessions.
  - This is the realistic agent workflow: agents keep notes and reuse numbers days later.

### First shippable slice

- **Public lane.** Outbound records for `fmine assure public` renders and MCP answers. Recipients are artifact ids
  and agent session ids, so no personal data is involved.
- **Recall by Claim and by revision.**
- **Size.** About 350 LOC (INFERENCE).

### Test

- **Oracle by construction** (property test):
  - set-up: three revisions × N outputs; mark one revision defective and supersede k Claims;
  - expected: `recall` returns exactly the outputs whose revision is defective or whose Claims include a
    superseded one.
- **Agent lease task (GATE-ROBOT-01).**
  - Set-up: an agent caches an answer, and the Claim is then superseded.
  - Pass: the agent revalidates before reuse.
  - Fail: it reuses the stale figure.
- **Replay.** List every output of revision `68e7091`'s fallback path from the run history.

### What could kill it

- **Low coverage.** If most figures leave by copy-paste or screenshot, the register sees a minority.
  - Measure: run CC-04 lint on a sampled board pack and count the share of figures that carry a resolvable Claim
    token.
  - Rule: below 50% after one quarter, drop the recipient half and keep revision recall.
- **Privacy.** Recipient identities are personal data. They stay in the tenancy under a retention limit, and none
  enters this repository.

### Self-score: **590**

## B4. Salted review: measure whether sign-off catches errors

### The blind spot

- **The plan's safety case rests on people.**
  - INV-002's flags stay false, so a human signs.
  - QPs sign.
  - A named reviewer pool judges GATE-BULL-01 (§37.3).
- **All 45 ideas assume a sign-off means someone checked.** Nothing measures whether reviewers catch errors, and
  the plan does not mention automation bias.
- **This project already shows the failure.** Beads were closed citing GATE-BULL-01 before any PASS existed, and
  closed beads with unmet done-when conditions "exist in number" (r7 C015, R002). The review accepted claims
  without checking them.

### Subsystems, user and workflow

- **Subsystems:**
  - Testpit (`fmine-gen` builds the seeds and holds the sealed key);
  - Helm (DecisionCard review);
  - Hallmark (QP review);
  - Bedrock (the key's hash is registered before review, INV-008).
- **Users:**
  - the GATE-BULL-01 reviewers, QPs and finance reviewers;
  - the board and audit committee, who rely on sign-offs;
  - agent reviewers, such as agents closing beads.
- **Workflow.**
  - **The packet.** Each review packet carries k seeded defects from registered classes:
    - a mis-cited cell;
    - a refused cell shown as reproduced;
    - a basis switch;
    - a stale Claim shown as current;
    - a wrong cause class in the discrepancy register;
    - a close reason citing a test that does not exist.
  - **Disclosure.** Reviewers are told that seeds exist, but not which items they are.
  - **After the review.** The key is unsealed, and the catch rate is reported by class with Clopper–Pearson
    intervals.
  - **The floor.** A review below a pre-registered floor is recorded as "review not demonstrated" and does not
    count toward the gate.
- **The safety rule that r7 makes necessary.**
  - Seeds never alter an issuer figure. They live only in FrankenMining's analytical layer (citations, verdicts,
    explanations).
  - They carry a sealed marker, and every export or authority path refuses them, as FMINE-REF-301 refuses
    embargoed rows.

### First shippable slice

- **The M0 review packet.** Five seeds in the packet for the two named reviewers (§37.3).
- **The bead-close review.** Seeded close reasons in the record that agents check.
- **What five seeds can show.** 0 of 5 caught bounds the catch rate below about 52% (95% Clopper–Pearson,
  INFERENCE). That is weak as a measurement, but decisive as evidence that a review did not happen.

### Test

- **Synthetic truth.** Simulated reviewers with a known detection probability; the estimator must recover it
  within its interval.
- **Real.** The first two review rounds.

### What could kill it

- **Consent.** Reviewers decline.
- **It works.** The catch rate is high and stable for two rounds, in which case reduce it to occasional spot
  checks.
- **A leak.** Any seed reaches an export, in which case stop at once.
- **RULE 0.1.**
  - This is a check on a check, which is the pattern RULE 0.1 warns against.
  - It earns its place only while it stays a handful of seeds per review, and r7 shows the failure it measures
    happened here.
  - If it grows into a framework, kill it.

### Self-score: **540**

## 6. Facts found along the way (structure only, no content quoted)

These counts come from the 18 distinct public Barrick workbooks.

- **Hidden sheets.**
  - Every AISC workbook checked ships hidden sheets: one each in Q4 2024 and Q4 2025, two each in Q1 and Q2 2026.
  - Non-trivial values with no exact match on any visible sheet of the same file:
    - Q4 2024: 103;
    - Q4 2025: 72;
    - Q1 2026: 139 and 150;
    - Q2 2026: 123 and 136.
  - INFERENCE: the comparison is an exact string match, so these counts are upper bounds on values not shown.
  - The public lane must never cite them. The reader's quarantine already prevents that.
- **External links.** The Q1 and Q2 2026 AISC files each carry one external-link part with an absolute target path
  and 304 cached values. In the Q2 2026 file, 302 of the 304 also appear elsewhere in the same file.
- **Author metadata.** Every workbook carries a populated last-modified-by field in `docProps`. That is an author
  identity field, so it counts as personal data under plan §31.2. The code does not read `docProps` today (no
  match in `crates/`); a one-line rule in §31.2 should keep it that way.
